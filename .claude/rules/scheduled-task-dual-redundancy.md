# 定时任务双冗余规则（Scheduled Task Dual Redundancy）

> 优先级：高
> 创建：2026-07-06
> 核心理念：一套定时任务 = 单点故障。两套独立系统 = 互为冗余。

---

## 背景

生产环境中的关键周期性操作如果只依赖单一调度系统，一旦该系统故障，整个保护体系停摆。

双冗余设计：AI定时任务 + 操作系统任务计划程序，各运行一套相同逻辑，互不依赖。

---

## 双冗余架构

```
AI 定时任务（每4小时触发）
  ├── 00:01 分支创建
  ├── 00:05 分支合并
  ├── 23:55 Zip快照
  └── 其他周期性任务

操作系统任务计划程序（独立调度）
  ├── 00:01 分支创建（独立脚本）
  ├── 00:05 分支合并（独立脚本）
  ├── 23:59 Zip快照（独立脚本）
  └── 其他周期性任务

两者互不通信、互不依赖 -> 任一套故障不影响另一套
```

---

## 铁律

### 铁律 1：关键操作必须双调度

以下操作必须同时注册到两套调度系统：
- 文件备份/快照
- Git 分支自动创建/合并
- 数据完整性检查
- 安全扫描

### 铁律 2：双系统互不感知

- AI任务不检查操作系统任务是否成功
- 操作系统任务不检查AI任务是否成功
- 各自独立运行，各自独立记录日志
- 禁止在其中一套里写「如果另一套已执行则跳过」

### 铁律 3：任务设计最小化

- 每一层只用一个任务
- 一条 prompt 同时处理多个目标目录
- 以节省 token 为目标

### 铁律 4：故障检测独立

- 两套系统各自记录执行日志
- 由独立健康检查检测「两套是否都失败了」
- 双重失败时才告警（单套失败不告警）

---

## 故障场景与恢复

| 场景 | AI系统 | OS系统 | 结果 |
|------|--------|--------|------|
| AI系统故障 | FAIL | OK | OS兜底，无数据丢失 |
| OS任务停摆 | OK | FAIL | AI兜底，无数据丢失 |
| 两者同时故障 | FAIL | FAIL | 触发告警，人工介入 |
| 两者都成功 | OK | OK | 冗余执行，幂等无副作用 |

---

## 监控检测

- [ ] 每天至少有一套系统的日志有当天记录
- [ ] 连续2天两套系统都无记录 = 告警
- [ ] 每周检查一次任务注册状态
