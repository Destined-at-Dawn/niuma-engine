[English](README.en.md) | 中文

## 我为什么写这个

2026 年 5 月，我在用 Claude Code 管多个工作区、上百个 skill。效率很高，但事故频发。

下面这些事，每一件都在 30 天内真实发生过：

1. **AI 说"已记录"但根本没落盘**。我信了，到下次对话发现什么都没有。——从此有了「证据分层」
2. **AI 给了一个异常好的数字**，声称"优化后准确率 98%"。细查发现它只挑了 N=8 个变体中最好的那一个。——从此有了「防假象审计」
3. **同一个参数调优方向，连续 3 个对话重复走了同样的弯路**。因为前面的对话压缩后，失败记录丢了。——从此有了「负结果归档」
4. **脚本差点删了 Windows 系统启动目录**。只差一个 UAC 弹窗。——从此有了「脚本安全检查」
5. **两个 background agent 同时写同一个文件**，互相覆盖了半天才发现。——从此有了「隔离契约」
6. **AI 每次对话风格都不同**，有的啰嗦有的敷衍，我每次都要重新调教。——从此有了「身份一致性」

**10 条工程法则，不是设计出来的，是从 6 次事故中一条一条长出来的。**

每出一条事故 → 我写一条规则堵住 → 同类事故不再发生 → 但有新的事故冒出来 → 再写一条规则。

6 次事故后，这些规则彼此之间形成了连接，变成了一个完整的框架。我就把它开源了。

---

## 这不是什么

❌ 不是"又一个提示词模板"
❌ 不是"让 AI 变聪明"的魔法
❌ 不是闭着眼装上就能用的插件

**这是一个纪律框架。** 它不会让 AI 变聪明，但它会让 AI **少犯错，犯了错能被抓住，同样的错不犯第二次。**

## 10 条核心工程法则——它们是怎么连起来的

如果把 10 条法则比作一个工程师的工作流，它们是这样协作的：

```
拿到任务
  → 法则10 先问「是新问题还是老套路？」          ← Think Before Act
      ↓
  → 法则3 实测，别凭直觉说「越大越好」           ← 实测优先
      ↓
  → 法则5 跨系统传数据时先校验格式               ← 跨边界校验
      ↓
  → 法则6 多个 Agent 并行时隔离写入区             ← 隔离契约
      ↓                                           ← 工具自由度
  → 法则4 别用人工 hint 绑死工具
      ↓
声称「做完了」之前：
  → 法则1 每个"通过"带口径标签                   ← 证据分层
  → 法则2 看到异常好数字先审"怎么来的"          ← 防假象审计
  → 法则8 过完全部门禁才算完成                    ← 门禁文化
      ↓
  → 法则9 同一目标多次失败就停，判结构墙         ← 识别结构墙
      ↓
交付时：
  → 边界声明：确知什么 / 不确定什么               ← 边界声明（独立规则）
      ↓
复盘时：
  → 法则7 死路归档，防止下个对话重踩              ← 负结果归档
  → 法则10 经验结晶成规则                          ← 规则结晶
```

**这 10 条是核心法则，是一条流水线上的 10 个检查点。** 仓库共包含 29 条规则——10 条核心法则贯穿全流程，其余 19 条是针对特定场景（Agent 管理、Skill 治理、安全运维等）的专项纪律。

没有法则 2，"通过"可能全是假象。没有法则 7，每个新对话都要重新踩坑。没有法则 6，多 Agent 就是互相捣乱。

### 每条法则对应什么痛点

| 你遇到过这种事吗 | 需要的法则 |
|----------|--------|
| AI 说"测试通过了"但你不确定意味着什么 | 法则 1：证据分层 |
| AI 给了一个异常好的数字，你直觉觉得不对劲 | 法则 2：防假象审计 |
| 调参数时 AI 说"越大越好"，但实际不是 | 法则 3：实测优先 |
| 你忍不住想用很多硬约束去限制 AI | 法则 4：工具自由度 |
| 两个工具之间的数据传过去就乱码了 | 法则 5：跨边界校验 |
| 两个 AI 同时改代码互相覆盖 | 法则 6：隔离契约 |
| 走了弯路，不想下次再走 | 法则 7：负结果归档 |
| AI 说"做完了"但你觉得还有很多问题 | 法则 8：门禁文化 |
| 同一个问题反复尝试反复失败 | 法则 9：识别结构墙 |
| 每次对话 AI 的表现都不一样 | 法则 10 + 纪律框架（规则一致性） |

## 三层记忆：不只是"记住"，是"知道该信多少"

comemo 做了很好的记忆分层设计，但它没有回答一个问题：**记忆的可信度。**

```
L3 全局规则（始终生效）
  └── L2 项目记忆（按项目加载）
       └── L1 个人记忆（按需加载）

每条记忆 = 内容 + 置信度标签 + 失效条件
```

- **[高置信]** — 用户明确说过 ≥ 2 次，或明确要求记录
- **[中置信]** — AI 观察到的规律，待用户确认
- **[待确认]** — 单次观察，不写入长期记忆（防过度沉淀）

**置信度不是装饰。** 它决定了 AI 做决策时对这条记忆的依赖程度。高置信的记忆 = AI 可以直接照做。待确认的记忆 = AI 必须再问一遍。

这和 comemo 不冲突。你可以先用 comemo 管记忆，再用 niuma-engine 管纪律。

## 6 阶段生命周期：AI 协作的全流程

这 10 条法则不是悬浮在空中的——它们嵌在 6 个阶段里：

```
1. 立项调研 — 这任务到底要做什么、不做什么
    ↓
2. 方案探索 — 铺开候选方案，不过早收敛
    ↓
3. 并行攻坚 — 多 Agent 隔离写入、独立验证
    ↓
4. 分层验证 — 每个"通过"带口径、高分先审计
    ↓
5. 复盘结晶 — 死路归档、经验升级为规则
    ↓
6. 交付声明 — 边界清单：确知/不确定/不知道
```

每个阶段有明确的目标产出 + 出口门禁 + 反模式警告。**不是建议，是 checklist。**

## 快速开始

### 你不需要全装

这是我设计的核心理念：**按痛点安装，不按功能安装。**

| 你的核心痛点 | 只需装这几条规则 |
|---------|---------|
| AI 给的数字不可信 | `anti-illusion-audit.md` |
| AI 说"做完了"但质量不行 | `10-engineering-laws.md` + `lifecycle-sop.md` |
| 同一个坑反复踩 | `negative-results.md` |
| AI 输出太长太啰嗦 | `anti-info-overload.md` |
| AI 每次对话风格不一样 | 自建风格指南 + `10-engineering-laws.md`（方法论一致性） |
| 脚本差点删错东西 | `script-safety-check.md` |
| AI 偷偷覆写文件 | `no-blind-overwrite.md` |
| 想从零搭建完整纪律体系 | 全装 `.claude/rules/`（共29条） |

**为什么用痛点不用功能来分类？** 因为如果我列"十个超强功能"，你不会知道哪个是你真正需要的。但如果我问"你被 AI 的假成绩坑过吗"，你立刻就知道了。

### 安装

```bash
git clone https://github.com/Destined-at-Dawn/niuma-engine.git
cd niuma-engine
```

然后让你的 AI 代理自己读 `docs/agent-install.md`。**让 AI 自己装自己，这才对。**

支持的代理：
- Claude Code（`.claude/rules/` 自动加载）← 主要目标
- Codex / Cursor / Aider / Gemini CLI（通过 adapter 桥接）
